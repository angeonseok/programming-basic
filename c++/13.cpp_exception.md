# 🔷 C++ 기초 문법 — 예외 처리

> 실행 중 발생하는 오류를 **프로그램을 죽이지 않고** 처리하는 메커니즘. 개념은 파이썬과 같지만 문법이 다르다 (`try/catch/throw`).
>
> 💡 **코테 관점:** 예외 처리를 적극적으로 쓰는 문제는 드물다. 하지만 **런타임 에러의 원인**(범위 초과, `stoi` 실패 등)을 이해하는 건 디버깅에 중요하다. 표준 예외가 어떤 상황에서 나는지 위주로 알아두자.

---

## 컴파일 에러 vs 런타임 에러

| 종류 | 시점 | 예시 |
|------|------|------|
| 컴파일 에러 | 빌드 단계 | 세미콜론 누락, 타입 불일치, 미선언 변수 |
| 런타임 에러 | 실행 중 | 0으로 나눔, 배열 범위 초과, 널 포인터 역참조 |

> 컴파일 에러는 빌드가 안 되니 바로 안다. **예외 처리는 런타임 에러**를 다룬다.

> ⚠️ **코테에서 "런타임 에러(RE)" 판정의 흔한 원인:**
> - 배열/벡터 **범위 초과** 접근 (`v[i]`에서 `i`가 범위 밖)
> - **0으로 나누기** (`a / 0`, `a % 0`)
> - **스택 오버플로** (너무 깊은 재귀)
> - 빈 컨테이너에 `top()`/`front()`/`pop()`
> - 널 포인터 역참조
> - **잡지 않은 예외** (`stoi("abc")`, `v.at(100)` 등에서 던진 예외를 `catch`하지 않으면 프로그램이 종료된다)
>
> 반대로 **정수 오버플로는 RE가 아니다.** 프로그램은 멀쩡히 끝나고 틀린 답(WA)만 낸다. 그래서 더 찾기 어렵다([02. 자료형 · 연산자](02.cpp_types_operators.md) 참고).

## try / catch / throw

> `try` 안에서 문제가 생기면 `throw`로 예외를 던지고, `catch`가 받아 처리한다. (파이썬 `try/except/raise`에 대응)

| C++ | 파이썬 대응 |
|-----|-------------|
| `try` | `try` |
| `catch` | `except` |
| `throw` | `raise` |

```cpp
#include <stdexcept>

try {
    int age = -5;
    if (age < 0) {
        throw runtime_error("나이는 음수일 수 없음");   // 예외 던짐
    }
} catch (const runtime_error& e) {          // 예외 받음
    cout << "에러: " << e.what() << "\n";    // e.what() = 메시지
}

cout << "프로그램 계속\n";   // 죽지 않고 실행
```

> 💡 `e.what()`은 예외 메시지를 돌려준다. catch는 보통 **참조(`const ...&`)**로 받는다(복사 방지).

### 복수 예외 처리

> 여러 종류의 예외를 각각 다르게 처리. `...`는 모든 예외를 받는다.

```cpp
try {
    // ...
} catch (const out_of_range& e) {   // 구체적인 것 먼저
    cout << "범위 초과\n";
} catch (const exception& e) {       // 포괄적인 건 뒤에
    cout << "일반 예외: " << e.what() << "\n";
} catch (...) {                       // 그 외 전부
    cout << "알 수 없는 예외\n";
}
```

> ⚠️ `catch`는 **위에서부터** 검사하므로, 구체적인 예외를 먼저 두고 포괄적인 `exception`을 뒤에 둬야 한다. (파이썬 except 순서 원칙과 동일)

## 참고

### 표준 예외와 발생 상황 (코테 디버깅용)

> 표준 예외들은 `std::exception`을 **상속**한 클래스다. 코테에선 이 예외들이 **언제 던져지는지** 아는 게 실전에 도움 된다.

| 예외 | 발생 상황 | 코테 관련 |
|------|-----------|-----------|
| `out_of_range` | 범위 초과 | `v.at(i)`, `s.at(i)`가 범위 밖일 때 |
| `invalid_argument` | 잘못된 인자 | `stoi("abc")` (숫자 아님) |
| `out_of_range` | 값 범위 초과 | `stoi("99999999999")` (int 초과) |
| `runtime_error` | 실행 중 논리 오류 | 직접 `throw`할 때 |
| `bad_alloc` | 메모리 할당 실패 | 지나치게 큰 `new`/`vector` |

> 💡 **`v[i]` vs `v.at(i)`:** `v[i]`는 범위를 넘어도 검사 없이 그냥 접근(쓰레기 값/크래시)한다. `v.at(i)`는 범위를 넘으면 `out_of_range` 예외를 던진다. **디버깅 중엔 `.at()`이 원인을 빨리 찾게 해준다**(단 약간 느려서 제출 코드는 `[]`를 쓰는 편).

```cpp
vector<int> v = {1, 2, 3};
// v[5];      // ❌ 범위 초과 (검사 없음, 위험)
// v.at(5);   // ❌ 범위 초과 → out_of_range 예외 (원인 파악 쉬움)
```

### stoi 예외 방어

> 입력 파싱에서 숫자가 아닌 문자열을 `stoi`하면 예외가 난다. 입력이 불확실하면 `try/catch`로 감싼다.

```cpp
try {
    int n = stoi(token);   // "abc"면 invalid_argument
    // n 사용
} catch (const exception& e) {
    // 숫자가 아닌 경우 처리
}
```

### 사용자 정의 예외

> `std::exception`(또는 그 자식)을 상속해 직접 예외 타입을 만든다. ([11. 객체 지향](11.cpp_oop.md)의 상속과 연결)

```cpp
#include <stdexcept>

class BalanceError : public runtime_error {
public:
    BalanceError(const string& msg) : runtime_error(msg) {}   // 부모에 메시지 전달
};

try {
    throw BalanceError("잔액 부족");
} catch (const exception& e) {     // 부모 타입으로 받기 가능
    cout << e.what();   // 잔액 부족
}
```

> 💡 코테에선 사용자 정의 예외를 만들 일이 거의 없다. 예외의 상속 구조(`exception`이 모든 예외의 부모)를 이해하는 예 정도로 보면 된다.

### 런타임 에러 원인 찾기 — 디버깅용 컴파일 옵션

> `v[i]` 범위 초과처럼 **예외가 안 나고 조용히 망가지는** 버그는 컴파일 옵션으로 잡을 수 있다. 내 PC에서 테스트할 때만 켜고, 제출 코드엔 영향이 없다.

```bash
# 표준 컨테이너의 범위 초과·잘못된 반복자 사용을 검사 (GCC, Windows MinGW에서도 동작)
g++ -std=c++17 -Wall -Wextra -g -D_GLIBCXX_DEBUG sol.cpp -o sol

# 메모리 오류 + 정의되지 않은 동작(오버플로 등) 검사 (Linux/macOS)
g++ -std=c++17 -Wall -Wextra -g -fsanitize=address,undefined sol.cpp -o sol
```

| 옵션 | 잡아주는 것 |
|------|-------------|
| `-D_GLIBCXX_DEBUG` | `vector`·`string` 등의 `[]` 범위 초과, 빈 컨테이너 접근, 무효 반복자 |
| `-fsanitize=address` | 배열 범위 초과, 해제된 메모리 사용 |
| `-fsanitize=undefined` | 부호 있는 정수 오버플로, 0으로 나누기 등 |

> 💡 문제가 생기면 **어느 줄에서** 터졌는지 알려준다. "로컬에선 맞는데 제출하면 RE"일 때 가장 먼저 해볼 일이다. (Windows의 MinGW g++에선 `-fsanitize`가 지원되지 않는다. WSL이나 온라인 컴파일러를 쓰거나 `-D_GLIBCXX_DEBUG`만 써라.)
